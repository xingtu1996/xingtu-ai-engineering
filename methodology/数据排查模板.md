# 方法-数据排查模板（Data Investigation）

> 定义：**数据排查（Data Investigation）** = 从"数据不对"现象出发，用 SQL 证据链定位根因的流程。先定证据链再下结论，**SQL 单点确诊 ≠ 全量同因**。

## 一、深入浅出
**本质**：数据不对 = 先定证据链再下结论。一条 SQL 确诊单个订单 ≠ 全量同因，必须先查影响面再定性。

**反模式**：

| 症状 | 后果 |
|------|------|
| 凭印象猜根因，无 SQL 佐证 | 结论无据，返工 |
| 单点当全量（BCI 排查原则） | 修复只覆盖个例，同因批量漏 |
| 改数据不溯源（直接 UPDATE 不清业务链路） | 数据"修对"但链路再写错，二次污染 |

## 二、示例企业实践

| 实践 | 落地 |
|------|------|
| db-knowledge 定位表结构 | 先查 `db-knowledge/db-tables-index.md`，再 grep 代码/DDL（TOK-001，不闭门造车） |
| pma-sql 只读查询 | 生产只读走 `pma-sql.sh`，禁裸连生产写库 |
| SQL 证据链 | 每条结论 = SQL 结果 + 时间戳 + 来源（代码/日志）三证据 |
| 单点≠全量 | BCI 排查原则：单点确诊后必查全量影响面，区分"个案"与"批量同因" |
| 时间戳来源 | 数据证据带查询时间 + 环境（dev/qa/prod），防跨环境误判 |

## 三、骨架

```
现象（单号/时间/异常值）
  → 相关表定位（db-knowledge 索引 + grep DDL/代码）
  → SQL 验证（pma-sql 只读，先查单点）
  → 数据对比（单点 vs 全量 COUNT + 正常值对照）
  → 根因（代码引用 file:// 路径:行号 + 数据佐证）
  → 修复影响面（订单数/下游消费者/幂等回滚）
```

## 四、检查清单

```
□ 证据链闭合？每条结论有 SQL+时间戳+来源，无凭印象？
□ 单点 vs 全量区分？单点确诊后查了影响面 COUNT？
□ 来源时间戳？查询时间+环境已标注，无跨环境误判？
□ 修复影响面评估？涉及订单数/下游/MQ 消费者已查？
□ 生产只读？走 pma-sql.sh，未直接写生产库？
```
