# 方法-接口自动化测试（API Automation Testing）

> 定义：**接口自动化测试（API Automation Testing）** = 对 HTTP 接口发请求，校验入参/返回/状态码/契约，测"接口合不合约"。
> 备案：测试金字塔 L2 API 契约层｜api-case.json.tmpl｜contracts/。

## 一、深入浅出

**本质**：把接口当"输入→输出"黑盒，测入参合规、返回合约、状态码合预期——测接口与调用方的握手协议。

**反模式**：① 只测 200 不测异常/边界；② 只看状态码不校验响应体 → 结构漂移静默。

## 二、示例企业实践

| 实践 | 落地 | 位置 |
|------|------|------|
| validator curl | AC 派生 TC-API-01…，L2 ≥3 条 | `specs-rules.md` §5.4 |
| Schema 漂移即红 | contracts/*.schema.json + validate-contracts.sh | `contracts/` |
| 可执行用例模板 | steps/assert_http/body/db/cleanup | `test/templates/api-case.json.tmpl` |

落点：① 无 Response 包装，JSONPath 按实际结构写（勿照抄 `$.code`）；② mutating 必带 cleanup + idempotent；③ 契约样例 `dc-refund.gifts-materials-inbound.schema.json`（additionalProperties:false）。

## 三、骨架：用例结构

```
{case_id: TC-{Spec}-{AC} | layer: graybox | service | idempotent}
preconditions: SQL 数据准备
steps[]:  url | method | headers | body
assert_http:  {status: 200/400/…}
assert_body:  [{jsonpath+eq/ne/exists/contains}]
assert_db:    [{sql + expect rows/not_empty/value}]
cleanup: SQL 清理（mutating 三步必备）
```

用例三态：

| 形态 | 覆盖 | 示例 |
|------|------|------|
| 正常 | 主路径 200 + 字段断言 | 匹配返回 odoId 命中 |
| 异常 | 参数非法 4xx / 业务异常 | 缺 skuCode→400；库存不足 |
| 边界 | 空数据 / 极限 / 重复 | odoId=null；重复提交幂等 |

## 四、检查清单

```
□ 状态码？200 + 4xx/5xx 全覆盖？
□ 响应体？assert_body JSONPath 断言关键字段？
□ 契约？validate-contracts.sh 全绿？
□ 幂等？mutating 有 preconditions + cleanup，重复执行安全？
□ 落库？关键写操作 assert_db 验证数据落地？
□ 复用？落到 test/cases/<service>/graybox/<case_id>.json？
```
